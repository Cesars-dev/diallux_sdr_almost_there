## 2. Mechanism dossiers

Each dossier: how it works end-to-end → what it does NOT solve → reported tradeoffs. Quotes are from the cited primary source.

### D1. The two-moment turn contract (Deepgram — the canonical eager-EOT design)

**How it works.** Deepgram splits every turn into two moments: *thinking* and *committing*. At moderate STT confidence (`eager_eot_threshold`, range 0.3–0.9, unset by default) the agent "closes the utterance internally and sends the request to the LLM. The turn is not yet confirmed." At high confidence (`eot_threshold`, default 0.7) or after `eot_timeout_ms` (500–60000ms, default 5000) the turn confirms and the reply releases. The window between is the **speculative window**. If the user keeps talking, the server sends `UserStartedSpeaking`, drops the in-flight LLM stream, and discards the speculative reply. Critically: **"Agent audio (TTS): Yes [gated on confirmation]. Audio is held until the turn is confirmed, so the agent never speaks over a user who is still talking."** Function calls are the deliberate exception — they dispatch *inside* the window unless marked `defer_until_eot: true`. ([source](https://developers.deepgram.com/docs/voice-agent-speculative-replies), [configure](https://developers.deepgram.com/docs/configure-voice-agent), [Flux params](https://developers.deepgram.com/docs/flux/configuration))
**What it does not solve.** It does not decide *what* to say on a resumed turn (the LLM re-generates from scratch); it does not help when the STT stream itself dies (that's `KeepAlive`/reconnect); and eager-think only pays off if the LLM+TTS can finish inside the window — a slow first token eats the whole gain.
**Tradeoffs (documented).** "Reduces end-to-end latency but increases LLM calls"; `eager_eot_threshold` "lower values → earlier triggers, lower latency, more false starts"; "Use `EagerEndOfTurn` outputs to **draft**, not finalize"; "Cache prepared responses and reuse on `EndOfTurn` (transcript guaranteed to match)". The DIY guide is explicit that the simple EndOfTurn-only mode is the recommended starting point. ([DIY guide](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot))

### D2. Eager-think / confirmed-speak split (LiveKit preemptive generation)

**How it works.** LiveKit's `preemptive_generation` starts LLM work "as soon as a final transcript arrives, before the turn is confirmed," with `max_retries` 3 per turn (reset on turn completion) and `max_speech_duration` 10s (long utterances skip preemption because "long turns are more likely to mutate"). The telling default: **`preemptive_tts: false`** — "Also start TTS preemptively. Cuts more latency at the cost of wasted compute on cancellations." The platform ships LLM-preemption ON and audio-preemption OFF by default, which is precisely the D1 contract: think early, speak confirmed. The cancellation rule: "The preemptive response should be canceled when the final transcript changes." ([tuning guide](https://docs.livekit.io/agents/logic/turns/tuning), [troubleshooting table](https://docs.livekit.io/agents/logic/turns/tuning#troubleshooting))
**What it does not solve.** When preemption *does* fire and the transcript mutates, you pay for dead tokens/audio — LiveKit's own observability note says "Preemptive generation in particular doesn't always reduce latency, and the metrics tell you whether your changes are pulling their weight." It also does nothing for turn-*start* problems (interruption classification is a separate layer).
**Tradeoffs (documented).** Latency win only on turns that don't mutate; wasted compute when they do; `preemptive_tts: true` amplifies both. Their symptom table: "Agent reads a partial transcript and replies based on incomplete input → … Lower `max_speech_duration`… Lower `max_retries`."

### D3. Reminder as a tagged interaction type (Retell `reminder_required`)

**How it works.** When the caller goes quiet, Retell does **not** re-run the normal state machinery. It sends the custom LLM a request with `interaction_type: "reminder_required"`, and the documented recipe is to append a short instruction — "(The caller has gone quiet. Check in briefly.)" — so the model "nudges rather than answering a question nobody asked." The same WS, the same transcript, but a differently-*framed* round. The dashboard knob is "Reminder frequency: how often the agent will remind the user when the user is inactive." ([custom LLM guide](https://docs.retellai.com/integrate-llm/integrate-llm), [settings](https://docs.retellai.com/build/single-multi-prompt/configure-basic-settings))
**What it does not solve.** If the caller is silent because the STT stream is dead, a reminder just talks into the void (that's F2 territory — Retell's WS reconnect + keepalive laws handle that). It also doesn't stop a *model* from re-asking a scripted question inside a reminder — the framing instruction is prompt-soft, not structural.
**Tradeoffs.** The nudge is still a full LLM round on Retell's custom-LLM path (cost per nudge); the equivalent Vapi design avoids that entirely with `say.exact` (zero LLM calls — the nudge is verbatim). Retell's blog names the failure mode this must avoid: "The Premature Recoverer keeps checking if the caller is still there… By the third time, the caller's stopped trying to think." ([seven failure modes](https://www.retellai.com/blog/turn-taking-voice-ai-hidden-problem))

### D4. The idle ladder (Vapi `customer.speech.timeout` hooks + OpenAI `idle_timeout_ms`)

**How it works.** Vapi's hook system fires `customer.speech.timeout` after `timeoutSeconds` (1–1000s, default 7.5) of caller silence, capped at `triggerMaxCount` (1–10, default 3) with optional `triggerResetMode: "onUserSpeech"`. The documented production ladder: 10s → `say.exact` "Are you still there?"; 20s → `say.prompt` model-generated check-in; 30s → farewell + `endCall`. "Idle messages are automatically disabled during tool calls and warm transfers to avoid interrupting system processes." OpenAI's server-side equivalent: `idle_timeout_ms` (5000–30000, server_vad only) — "The model will effectively prompt the user to continue the conversation based on the current context," measured from `response.done` **plus audio playback duration**, emitting `input_audio_buffer.timeout_triggered`. ([Vapi idle messages](https://docs.vapi.ai/assistants/idle-messages), [hooks](https://docs.vapi.ai/assistants/assistant-hooks), [OpenAI Realtime API ref](https://platform.openai.com/docs/api-reference/realtime-server-events))
**What it does not solve.** Neither mechanism guarantees the caller *heard* the nudge (audio-path failures still need F2 machinery), and neither re-asks the *substantive* question — by design. The nudge is deliberately generic ("still there?"), because a substantive re-ask is exactly the loop amplifier.
**Tradeoffs (documented).** Vapi: "Shorter timeouts create more responsive conversations but may interrupt users who need more time to respond" — and the default 7.5s with max 3 triggers bounds the nudge count structurally. Their timing guidance: 5–10s transactional, 10–20s support, 20–30s complex topics, plus "allow 2–3 seconds of audio processing time when choosing timeout values."

### D5. Monotonic response supersession (Retell `response_id`)

**How it works.** Retell's orchestrator is the sole owner of "the turn." It "asks for a response as soon as the caller sounds finished, which keeps the silence short by starting your generation before a response is expected. The cost is that some requests get discarded: when the caller was only pausing mid-thought and keeps going, Retell drops the pending response and asks again with a higher `response_id`." Acceptance rule: "Retell accepts content only for the `response_id` it most recently requested… Content sent under an older `response_id` is dropped without an error, so a discarded response can never reach the caller." There is no buffer dump, no socket reset, no transcript re-anchoring — **the STT stream is never touched by a cancellation.** ([handle discarded responses](https://docs.retellai.com/integrate-llm/integrate-llm#handle-discarded-responses))
**What it does not solve.** A discarded generation still costs tokens unless you abort early ("Stopping a discarded generation early is still worth doing"); Retell pushes that duty to your server via the staleness check. It also presumes the transcript the orchestrator sends is final-quality (their transcription-mode knob decides that separately).
**Tradeoffs.** Speculation cost vs silence: "keeps the silence short… The cost is that some requests get discarded." The FAQ is blunt about ownership: "Why does the agent talk over the caller, or wait too long? That's turn-taking, which Retell controls, not your LLM."

### D6. Confidence-band transcript firewall (Vapi `endpointedSpeechLowConfidence`)

**How it works.** Vapi classifies every endpointed transcript by STT confidence into three bands. With a transcriber `confidenceThreshold` of 0.4 (typical): **≥ 0.4 → processed normally; 0.2–0.4 → hook fires** (default action: "I'm sorry, I didn't quite catch that. Could you please repeat?"); **< 0.2 → discarded** — it never reaches the LLM. The hook supports banded handlers via shorthand (`[confidence=0.2:0.4]`, `[confidence=0.3:0.4]`) so different bands get different asks, and options `confidenceMin`/`confidenceMax`. Supported for transcribers with `confidenceThreshold` config: Deepgram, Gladia, AssemblyAI. ([assistant hooks](https://docs.vapi.ai/assistants/assistant-hooks))
**What it does not solve.** It cannot resurrect audio the denoiser destroyed (Vapi's own docs route that to denoising-mode tuning — "missing short responses (e.g. 'sure', 'yes')… try No denoising"); and the discard band means genuinely-quiet-but-correct transcripts get dropped by design — you trade recall for precision.
**Tradeoffs.** The band widths are fixed by the formula (floor = `confidenceMax − 0.2`, minimum 0); the "please repeat" reply costs a turn of caller patience; and it only exists for endpointed (final) transcripts — partials never get this treatment.

### D7. Backchannel discrimination (Vapi `acknowledgementPhrases` + LiveKit adaptive interruption & false-interruption recovery)

**How it works.** Vapi: `stopSpeakingPlan.acknowledgementPhrases` ("okay", "right", "uh-huh", "yeah", "mm-hmm", "got it") — on interruption evaluation, acknowledgement phrases → **ignore interruption**; `interruptionPhrases` → instant pipeline clear. LiveKit goes further: `interruption.mode="adaptive"` uses an audio model that "analyzes the acoustic signals to determine whether the agent should actually yield the turn" — distinguishing barge-ins from "conversational backchanneling… 'uh-huh,' 'okay,' 'right' that indicate attention but don't require a response," faster than waiting for a transcript. And the recovery net: `false_interruption_timeout` (default 2.0s) — "Silence window after a detected interruption before it's classified as false. After this elapses with no transcript, the agent can resume" — with `resume_false_interruption: true` (default) **resuming the interrupted speech**. ([Vapi voice pipeline](https://docs.vapi.ai/customization/voice-pipeline-configuration), [LiveKit adaptive](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling), [LiveKit tuning](https://docs.livekit.io/agents/logic/turns/tuning))
**What it does not solve.** Phrase lists are language-bound and brittle to accents ("uh-huh" vs "mm"); the audio model requires LiveKit Cloud (or dev mode) plus a VAD-equipped session. Neither approach answers *what the agent says next* after a true backchannel — that's prompt/flow design.
**Tradeoffs (documented).** LiveKit's symptom table: "Agent is interrupted by short acknowledgments → Switch interruption.mode to adaptive. Raise min_words or min_duration. Confirm false_interruption_timeout and resume_false_interruption are at their defaults so the agent resumes after silent false positives." Vapi's own note: higher `interruption` resilience "will hinder the ability of your agent getting interrupted, so it's a trade-off."

### D8. Post-interrupt backoff (Vapi `backoffSeconds`)

**How it works.** After a true interruption, Vapi blocks **all** assistant audio for `backoffSeconds` (0–10s, default 1.0): "User Interrupts → Assistant Audio Stopped → backoffSeconds Blocks All Output → Ready for New Input." It is explicitly a recovery period, sequenced before normal flow resumes ("`backoffSeconds` completes first, then normal flow resumes with `waitSeconds`"). Documented recovery math: interruption at t=1.2s → backoff ends 2.2s → new input processed → response at ~4.2s. ([voice pipeline configuration](https://docs.vapi.ai/customization/voice-pipeline-configuration))
**What it does not solve.** It adds dead air by design (that's the point — cede the floor); it does not decide whether the interrupting speech was real (that's D7's job); and it can't help if the caller's answer itself gets eaten by STT (that's D6/D1).
**Tradeoffs.** Documented guidance: 0.5s quick-recovery, 1.0s "natural pause for most conversations," 2.0s formal settings. Too high and the agent feels sluggish after every barge-in; too low and you re-enter the talk-over collision that produced our F1 fragments.

### D9. Latency fillers, one-shot per turn (ElevenLabs `soft_timeout` + Vapi request-start messages)

**How it works.** ElevenLabs: when the LLM takes longer than `soft_timeout` (0.5–8.0s, recommended 3.0s, default −1 = disabled), the agent speaks a filler — static default `"Hhmmmm...yeah."` or a lightweight-LLM-generated one ("uses recent conversation context (up to 4 messages, 1000 characters) to generate relevant fillers"). "Soft timeout triggers only once per turn to prevent multiple fillers in succession." Vapi's equivalent is `request-start` messages on tool calls, with documented defaults ("Hold on a sec", "One moment", "Just a sec"…). ([ElevenLabs conversation flow](https://elevenlabs.io/docs/eleven-agents/customization/conversation-flow), [Vapi API spec](https://docs.vapi.ai))
**What it does not solve.** It masks LLM latency, not STT death or TTS failure; and ElevenLabs explicitly warns "Avoid time indicators in filler messages (e.g. 'One second...') as actual response times are unpredictable."
**Tradeoffs.** One-shot-per-turn bounds the annoyance; LLM-generated fillers add a (small) extra call with a static fallback; static fillers risk feeling canned on repeat calls.

### D10. Said-truth context commit (Pipecat)

**How it works.** Pipecat's interruption teardown runs in strict order: the `InterruptionFrame` (a SystemFrame, handled immediately rather than queued) makes every processor cancel current work; the in-flight LLM completion is cancelled mid-stream; TTS clears its text aggregation and word timestamps; the output transport "drains its audio queue, discarding audio that was generated but not yet played." Then the key law: **"Only the words that were actually spoken" end up in the LLM context** — "As the bot speaks, the output transport pushes `TTSTextFrame`s downstream in sync with audio playback. Text that never played never reaches the assistant context aggregator. On interruption, the aggregator commits the partial, spoken-so-far text to the context as the assistant message." Observable via `on_assistant_turn_stopped` with `message.interrupted` and the committed content. Uninterruptible frames (`FunctionCallResultFrame`, `EndFrame`) are preserved through the teardown. ([Pipecat interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions))
**What it does not solve.** It fixes the *belief* side (what the model thinks it said), not the *audio* side — a cut-off sentence is still cut off; and if your transport can't report word-level playback position, you can't implement it precisely.
**Tradeoffs.** The context now contains truncated assistant turns by design — prompts must tolerate that (or the model will "apologize" for sentences it never finished). This is the structural alternative to our dedupe/clamp filters: keep belief and audio identical by construction instead of filtering speech after the model chose it.

### D11. Sticky fallback + keepalive/reconnect laws (Retell + Vapi per-stage lifecycle)

**How it works.** Retell's TTS fallback: if the primary voice fails mid-call, "it will use the same gender voice as the original voice… and fallback to the next voice in the list… even if the original voice is back online, the agent will still continue with the fallback to minimize change of voice during the call." Platform voices get this automatically; custom voices require configuring a fallback chain (different providers, never the same one as primary). The LLM WS has a documented reconnect contract: 3 attempts, 7-second timeout each, 3 seconds apart; keepalive is an application-level `ping_pong` interaction you **must** echo, with a named error taxonomy (`error_llm_websocket_open` / `lost_connection` / `runtime` / `corrupt_payload`) and the 1006-rebuild behavior. Vapi exposes the same idea as hookable lifecycle events per pipeline stage: `assistant.transcriber.reconnecting`, `assistant.model.reconnecting`, `assistant.voice.reconnecting`. ([Retell TTS fallback](https://docs.retellai.com/build/tts-fallback), [WS troubleshooting](https://docs.retellai.com/integrate-llm/troubleshooting), [Vapi hooks](https://docs.vapi.ai/assistants/assistant-hooks))
**What it does not solve.** Voice-switch fallback is audible (mitigated by stickiness, not eliminated); the reconnect contract covers the *signaling* WS, not a zombie STT media socket that stays open but silent — for that, only a liveness probe (KeepAlive + deadline, or bytes-received watchdog) works.
**Tradeoffs.** Retell's warning about their most aggressive denoise mode doubles as the general caution: aggressive preprocessing "may suppress or distort the caller's speech… dropped, clipped, or distorted transcription." Fallback chains cost voice consistency; keepalives cost a few bytes/sec.

## 3. Who owns "the turn" (Q6 answer — the architectural takeaway)

Across all six platforms the answer is unanimous, and it is the single biggest structural difference from our engine:

1. **A turn-taking component owns the turn — never the LLM, never the TTS, never the graph.** Retell: "That's turn-taking, which Retell controls, not your LLM." ([source](https://docs.retellai.com/integrate-llm/integrate-llm)) Deepgram: the STT's two-moment contract decides think/commit. Vapi: the `startSpeakingPlan`/`stopSpeakingPlan` stage machine. Pipecat: user-turn strategies. OpenAI: server turn detection (or deliberately null'ed).
2. **STT finals reach the LLM only on a FINAL (or contractually-equal eager) transcript.** Retell sends only finalized utterances in `transcript`. Deepgram guarantees `EndOfTurn` transcript == `EagerEndOfTurn` transcript. Vapi discards below-confidence finals outright (D6). LiveKit preemption triggers "as soon as a **final** transcript arrives" — partials feed retrieval/UI, not turn commitment. **Nobody runs the main LLM round on raw partials.**
3. **Cancellation is supersession, not destruction.** When a speculative round loses, the platforms drop the *response* (response_id supersession at Retell; stream-drop at Deepgram; preemptive-cancel at LiveKit) and leave the input stream untouched. Our barge-in path cancels the turn task AND resets the transcript anchors (`_update_fired`, `_t_speech_growth`, `_last_update_len` — session.py:599–604) — the logical equivalent of dumping the STT buffer mid-speech, which is where the F1 fragment is born.
4. **Audio release is a separate gate from generation.** Deepgram holds TTS audio until turn confirmation; LiveKit defaults `preemptive_tts: false`. Generation can be eager; **speech is confirmed**.
5. **The latency budget they accept for this:** Retell ~600ms end-to-end including turn-taking (⚠️ blog claim, not a spec — see §7); Vapi's documented budget arithmetic: endpointing 0.2–0.6s (waitFunction-dependent) + LLM ~0.8s + TTS ~0.5s + `waitSeconds` 0.4s ≈ 1.9–2.3s total, with `endpointingLatencyAverage` exposed as a per-call metric; Retell's transcription "accuracy mode" costs "+roughly 200ms." None of them buy turn safety with TTS-side text surgery.

## 4. PORT LIST — smallest-change-first, one variable per mechanism, env-knob-first

Ranked by (expected fix × lines of code). Each port states the platform it copies, the single knob, and **what it DELETES from our code**. Nothing here touches prestack TTFT (the 630ms solved problem) — ports 1 and 5 are the only ones that touch the eager path, and both *remove* work from it.

### PORT 1 — Eager-think, confirmed-speak (copies Deepgram D1 + LiveKit D2 defaults)
**Fixes:** F5 (speculation/adoption mismatch), the talk-over half of F1, mid-speech audio collisions.
**Change (architectural):** on `EagerEndOfTurn`, keep starting the LLM round as today — but **hold the SentenceGate flush** (do not emit TTS audio). On `EndOfTurn` with equal transcript (already guaranteed by Deepgram's contract — the `eager_final_match` guard we wrote is enforcing a guarantee Deepgram already gives), release the gate. On `TurnResumed`, discard silently (no Twilio clear needed — nothing was spoken).
**One knob:** `EAGER_HOLD_AUDIO_UNTIL_CONFIRM=true` (default false = today's behavior; env-first, A/B by ear per your LAW).
**Latency math:** TTFT becomes (EndOfTurn − EagerEndOfTurn) + TTS-first-byte instead of TTS-first-byte from the eager start. Deepgram's own managed agent ships exactly this split, and LiveKit ships `preemptive_tts: false` for the same reason — this is the industry default, not a compromise. Measure the delta against the 630ms prestack number before/after with your existing `t_eager` spans (iter43 T1 already stamps it).
**DELETES:** the entire `_grace_then_cancel` path + `eager_resume_grace_ms` knob (iter46 T7) + the "eager turn cancelled (grace expired, user still talking)" branch (session.py:560–567) + the iter38 F1 race guard dance around `extra["eager"]` ordering (session.py:540–543). The grace window exists to avoid wasting a spoken-partial turn; if audio never released early, there is nothing to grace.

### PORT 2 — Nudge as a tagged reminder round, never a state round (copies Retell D3 + Vapi D4)
**Fixes:** F1's core loop amplifier (the re-prompt that asks the *same scripted question*).
**Change:** the pause timer (when it ships on main — PT-68/iter70 T2) must fire a round whose payload carries `interaction_type: "reminder"`; the prompt for that round is a one-line directive ("The caller has gone quiet — check in briefly, do not re-ask your last question") appended after history, NOT the state's question machinery; and the turn must not advance `rounds_left`/state gates. Cap it structurally like Vapi: max 2–3 per call, reset on user speech.
**One knob:** `PAUSE_REASK_MODE=reminder` (values: `off` | `reminder` | legacy `engine`).
**DELETES:** the "re-ask round always heavy + post-history directive" design from the iter68-lite port (c3022c3/651e567) and any future variant where the timer re-runs the state node. Also deletes the need for the "no-empty-user guard" to protect against the reminder itself becoming input — the reminder round is tagged, not transcripted.

### PORT 3 — Confidence-band ingest firewall (copies Vapi D6)
**Fixes:** the fragment half of F1 (fragment `user_text` → model re-asks), F5's fragment finals.
**Change:** at `_on_eot` / `_on_eager_eot` ingest, read the Deepgram confidence on the final transcript; band it Vapi-style: ≥ floor → run; band → speak one exact "Sorry, you cut out — could you say that again?" via TTS *without* an LLM round; below floor → drop silently and re-arm the pause timer.
**One knob:** `STT_CONFIDENCE_FLOOR=0.2` + `STT_CONFIDENCE_REASK_CEIL=0.4` (Vapi's documented defaults: ceiling = transcriber threshold ≈0.4, floor = ceiling − 0.2).
**DELETES:** every LLM round that would have run on a fragment. This is the structural kill for "user_text is fragment/empty → model re-asks": the model never sees the fragment.

### PORT 4 — Ack/backchannel filter on the barge-in path (copies Vapi D7 + LiveKit D7)
**Fixes:** F4 (transition silence after "yeah"), the false-barge-in share of F1/F3 (the "?"-glue after agent's own question — "yeah" mid-question spawns a turn that asks "sorry, what?" — and the stacked recounts).
**Change:** in `_on_start_of_turn`, before cancelling the running turn, hold the cancel for a short window and inspect the accumulating `Update` text: if it matches an ack list ("yeah", "okay", "right", "uh-huh", "mm-hmm", "got it", "sure") or produces no transcript within ~2.0s (LiveKit's `false_interruption_timeout` default), **resume the interrupted speech instead of yielding the turn**. Resuming = re-emit the remaining gated sentences of the cancelled turn (our SentenceGate already holds unflushed text; today it is discarded on `gate.reset()`).
**One knob:** `BARGE_ACK_FILTER=true` + `BARGE_FALSE_INTERRUPT_TIMEOUT_MS=2000` + `BARGE_ACK_PHRASES` (comma list, env-overridable).
**DELETES:** the transition-beat problem's *cause* (the flat ack that killed the agent's question) — which means the iter68/PT-70 `turn_asked` one-trip patch becomes a belt-and-suspenders rather than the load-bearing fix. It also retires the cross-turn `question_stem_window` machinery's reason to exist (the "?"-glue re-ask stops being generated).

### PORT 5 — Post-interrupt backoff (copies Vapi D8)
**Fixes:** the collide-re-speak component of F1 (agent re-prompts while the caller is still answering the re-prompt).
**Change:** after any real barge-in (Port 4 said it's real), block new agent audio for a fixed window before the next turn's TTS may start — the caller's answer gets the floor.
**One knob:** `POST_INTERRUPT_BACKOFF_MS=1000` (Vapi default 1.0s).
**DELETES:** nothing structural — it's a guardrail. But it makes Ports 2+3 safe by construction: even if a reminder fires while the caller starts answering, the backoff keeps the agent from talking over the answer that would otherwise become a fragment.

### PORT 6 — Said-truth history commit (copies Pipecat D10)
**Fixes:** the said-truth drift behind F3's stacked recounts ("Okay, so… you said 10-15, that's weekly?" — the model believes it said things that were cut) and F6's aftermath.
**Change:** on interruption, the assistant message written to history is **the spoken-so-far text** (what the gate flushed), not the LLM's full `content`. The gate already knows exactly what flushed; snapshot it into the history write at cancel time.
**One knob:** `HISTORY_SAID_TRUTH_ONLY=true`.
**DELETES:** the drift that motivated the entire dedupe family. With belief == audio by construction, `tts_dedupe_sentences`, `tts_dedupe_window`, `tts_dedupe_similar` (+ its overlap/min-words knobs), and the parked `tts_dedupe_semantic` lineage all become dead code candidates — **delete them only after a battery proves repetition stays dead via Ports 4+6**, since the model no longer sees unspoken text it wants to "finish."

### PORT 7 — Prewarmed-socket liveness probe (copies the KeepAlive/reconnect discipline of D11; your PT-68 note already names it)
**Fixes:** F2's adopted-zombie (39s audio, zero STT messages).
**Change:** before adopting a pooled STT socket, require proof of life: either an `Update`/`TurnInfo` observed within N ms of adoption, or send `KeepAlive` (deepgram_stt.py:169 already sends them on a timer) and require any inbound frame within the deadline; else discard the socket and connect fresh (the existing fallback path, session.py:210).
**One knob:** `STT_ADOPT_LIVENESS_TIMEOUT_MS=750`.
**DELETES:** the "never-mute revive" bolt-on's reason to exist for the STT-death class of mute (the TTS-death class is handled by the existing factory fallback + Retell-style stickiness if you add a fallback voice pin).

### PORT 8 — One-shot soft filler on LLM/tool latency (copies ElevenLabs D9; you already half-own this)
**Fixes:** the dead-air-behind-F1 (the 5–15s tool-chain silences the pause timer currently polices).
**Change:** promote the iter40 L3 "One moment while I check availability." filler from a slots-specific hack to a general rule: any round whose tools are still in flight after `SOFT_TIMEOUT` speaks one canned filler, **once per turn**, never model-generated (keep it deterministic — no extra LLM call).
**One knob:** `SOFT_FILLER_MS=3000` + `SOFT_FILLER_TEXT="One moment…"`.
**DELETES:** the pause timer's jurisdiction over tool waits — the timer then only handles true caller absence, at a longer, Vapi-laddered cadence (10s nudge / 20s prompt / 30s graceful close), which is Port 2's `reminder` mode.

**What the PORT LIST deliberately does NOT port:** (a) semantic/audio turn-detection models (Retell's proprietary model, LiveKit's TurnDetector, OpenAI's semantic_vad) — we already run Deepgram Flux EOT, which is the same class of signal and is *already* the input to our eager path; (b) Vapi's `waitFunction` sigmoid — it's a latency-shaping knob for a problem we don't have (we're not over-eager on EOT, we're over-eager on *audio release*); (c) any TTS-side text filtering — no platform does it, and §2/D10 explains why the alternative exists.
